# Research & Decisions: free-trial

## Как сейчас устроен код (проверено по исходникам)

- `/start` (`handlers/start.py`): рисует меню; пользователя в БД **не создаёт** (`User` создаётся только в `CreateOrderUseCase` через `get_or_create`).
- `CreateOrderUseCase`: `order_type = "topup"` если есть активный `VPNProfile`, иначе `"new"`. Решение фиксируется при создании заказа.
- `AdminUseCases.approve_order`: блокировка по `order_id` (in-process `asyncio.Lock`) + проверка `status == "pending"`. Ветка `topup` - `_apply_topup` (get_user -> план `calculate_renewal_plan` -> сохранение плана в `Order` -> reset -> PUT -> `completed`); при 404 от Marzban - fallback на ветку `new` (создание нового пользователя). Ветка `new` - `_apply_new_purchase` (inbounds -> create_user `user_{user_id}_{order_id}` -> `VPNProfile` -> `completed`).
- Хранилище: SQLite через async SQLAlchemy; **одна общая `AsyncSession`** на всё приложение (`main.py`), `Base.metadata.create_all` при старте, Alembic нет.
- Marzban: `MarzbanClient` (httpx) - `create_user`, `get_user`, `update_user`, `reset_user_data_usage`, `get_inbounds`. Единицы: ГиБ (`* 1024**3`), байты в API.
- Планировщика нет. `JobQueue` в PTB 22.8 присутствует как класс, но `apscheduler` не установлен (extra `job-queue` не подключён), поэтому `application.job_queue` был бы `None`.
- PTB по умолчанию обрабатывает апдейты **последовательно** (`concurrent_updates` не включён), но фоновая задача работает параллельно хендлерам в том же event loop.

## Decision 1: стык триала с `approve_order`

- **Decision**: триал-пользователь идёт по существующей ветке `topup`; решение «триал или нет» принимается **в момент подтверждения** (внутри блока вычисления плана), а не при создании заказа. Для триала вместо `calculate_renewal_plan` вызывается новая чистая функция `build_trial_conversion_plan(purchased_bytes, purchase_time)` (carried_over_bytes=0, `new_data_limit`=пакет, `expire`=+30 дней). Чистая функция переноса не меняется.
- **Rationale**: статус триала на момент создания заказа может устареть (два заказа подряд: первый конвертирует триал, второй уже платный перенос). План всё равно сохраняется в `Order`, поэтому идемпотентность `approve_order` сохраняется без изменений. `get_user` в триальной ветке остаётся как проба существования - чтобы работал существующий fallback при 404 (пользователь удалён в Marzban).
- **Alternatives considered**: (a) подать `current_status="expired"` в `calculate_renewal_plan` - хак, смешивает смыслы; (b) новое значение `order_type="trial_convert"` при создании заказа - может устареть; (c) правка чистой функции - запрещено условиями.
- **DI**: `AdminUseCases.__init__` получает необязательный `trial_repo=None` (поведение без него идентично текущему, существующие 13 тестов не меняются).

## Decision 2: порядок шагов подтверждения (идемпотентность)

`plan (сохранён) -> reset (чекпоинт) -> PUT -> mark_trial_converted -> order=completed -> сообщение`. `mark_trial_converted` идемпотентен; при падении между шагами повтор берёт сохранённый план и не пересчитывает остаток. Дополнительная защита: монитор уведомлений не пишет пользователям с подтверждённым заказом и «лечит» состояние (ставит `converted`).

## Decision 3: имя пользователя Marzban

- **Decision**: `user_{telegram_id}_trial`.
- **Rationale**: у триала нет заказа, схема `user_{telegram_id}_{order_id}` неприменима. Детерминированное имя позволяет при повторе найти уже созданного пользователя (`get_user`) и переиспользовать - нет дубликата.
- **Alternatives**: случайный суффикс - теряется идемпотентность.

## Decision 4: резерв записи и откат

Порядок: проверки права -> проверка суточного лимита и `INSERT` резерва под per-user и глобальным (для лимита) `asyncio.Lock` -> Marzban (проба/создание) -> атомарная транзакция «пользователь + `VPNProfile` + `status=active`». `UNIQUE(telegram_id)` на уровне БД - окончательная защита (при `IntegrityError` перечитываем запись и отвечаем как для повтора). Ошибка Marzban/БД -> `DELETE` резерва. Если откат не удался - резерв подхватывается следующим нажатием.

## Decision 5: доступ к БД из фонового задания и новых репозиториев

- **Decision**: `TrialRepository` принимает `async_sessionmaker` и на каждую операцию открывает **короткоживущую сессию** (транзакция = одна операция).
- **Rationale**: общая `AsyncSession` приложения не потокобезопасна для конкурентного использования корутинами (фон + хендлеры). Существующие репозитории не трогаем (вне scope), но фиксируем это как существующий риск.
- Для DI (конституция II): репозиторий создаётся в `main.py`, в use case только передаётся.

## Decision 6: планировщик

- **Decision (рекомендуется)**: простая `asyncio`-задача (`run_periodically`) внутри процесса бота, интервал 300 с, запускается после старта polling, отменяется при остановке. Нет новых зависимостей. Состояние (флаги, метки) в БД, поэтому перезапуск безопасен.
- **Alternative (нужно ваше согласие)**: `python-telegram-bot[job-queue]` - добавляет `apscheduler>=3.10.4,<3.12.0` и его транзитивные зависимости; даёт `application.job_queue.run_repeating`. Для одной периодической задачи избыточно.
- **Не выбрано**: `python-telegram-bot[rate-limiter]` (`aiolimiter`) - лимиты соблюдаем ручной паузой между сообщениями и обработкой `RetryAfter`.

## Decision 7: пакетный опрос Marzban

- **Decision**: `GET /api/users` с повторяющимся query-параметром `username` (массив строк, подтверждено в `docs/marzban_openapi.json`: operationId `get_users`, параметры `offset`, `limit`, `username[]`, `search`, `status`), порциями по 50 имён, `limit` = размеру порции. Ответ `UsersResponse {users: [...], total}`; в `UserResponse` есть `used_traffic`, `data_limit`, `expire`, `status`.
- **Rationale**: максимум ~350 одновременно активных триалов при лимите 50/сутки и сроке 7 дней = <= 7 запросов за цикл вместо 350.
- **Не проверено на живой панели**: поведение фильтра `username[]` в вашей версии Marzban и значение `limit` по умолчанию; в тестах - фейковый клиент.

## Decision 8: надёжность уведомлений

«Захват флага» условным `UPDATE ... WHERE notified_X_at IS NULL` (rowcount==1) **до** отправки: гарантирует «не более одного раза» даже при параллельных проверках и после рестарта. Платой за гарантию является возможная потеря сообщения при падении процесса именно между захватом и отправкой (принято). Временная ошибка отправки -> флаг снимается. `Forbidden` -> `bot_blocked_at`.

Лимиты Telegram: пауза ~50 мс между сообщениями (<= ~20 сообщений/с при лимите ~30/с), `RetryAfter` -> `sleep(retry_after + 1)` и до 3 повторов.

## Decision 9: единицы и время

1 ГБ = 1024^3 байт (как везде). Время в БД - naive UTC. Суточный лимит - скользящие 24 часа по `created_at`.

## Рефакторинг существующего кода (минимальный)

Единственное извлечение из существующего кода: сборка словаря inbounds из ответа `GET /api/inbounds` выносится в чистую функцию `build_inbounds_payload` (переиспользуется триалом и первой покупкой; `FakeMarzbanClient.get_inbounds` в существующих тестах не меняется).
