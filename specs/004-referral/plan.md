# Implementation Plan: referral

**Branch**: `feature/referral` (от `dev` 17d6d43, синхронна с `origin/dev`) | **Date**: 2026-10-08 | **Spec**: [spec.md](spec.md)

## Summary

Реферальная система по одноразовым ссылкам: привязка приглашённого, +15 ГБ к первому пакету (в план `Order`), 30% от денежной части пригласившему на бонусный баланс (append-only журнал), автоматическое списание баланса при покупке с **резервом при создании заказа** и возвратом при отклонении. Всё денежное - короткими атомарными SQL-транзакциями на SQLite; награда и перевод заказа в `completed` - одна транзакция.

## Technical Context

- Python 3.12, `python-telegram-bot` 22.x, SQLAlchemy 2 + aiosqlite, loguru, pytest + pytest-asyncio. **Новых зависимостей нет.** Линтеров нет.
- Baseline: `uv run pytest` -> **173 passed**, 9 warnings (PTBDeprecationWarning про `retry_after`, не наши).
- Время: naive UTC (`domain/clock.py`), месяц для лимита - календарный месяц UTC.
- Новые репозитории - на `async_sessionmaker` (как `TrialRepository`), не на общей сессии `main.py`: общая сессия не даёт транзакционной изоляции между хендлерами и фоновыми задачами.

## Дизайн

### 1. Ссылки и привязка

- Токен `secrets.token_urlsafe(16)` (22 символа, 128 бит), параметр `ref_<токен>` - 26 символов из `A-Za-z0-9_-`. Разбор: регэксп `^ref_[A-Za-z0-9_-]{16,60}$`, всё остальное - «нейтральный /start».
- Лимит 3 активных - условный `INSERT ... SELECT` (атомарно, см. data-model.md) плюс in-process lock по пригласившему для чистоты поведения.
- Привязка (`AcceptReferralUseCase`): одна транзакция: условный `UPDATE` ссылки (в нём же «нет платного заказа» и «не своя») -> `INSERT referrals`; `IntegrityError` по `invitee_id` откатывает и сгорание. Результат: `BOUND | NOT_BOUND` без причины наружу (причина - только в лог как категория, без токена).
- Имя бота: `BOT_USERNAME` из `.env`, иначе `await bot.get_me()` один раз с кэшем (после `application.initialize()` PTB и так хранит его); если имя недоступно - ссылку не выдаём, пользователю нейтральное «Попробуйте позже», в лог предупреждение.
- Опасное место логов: `IntegrityError`/`OperationalError` SQLAlchemy печатают `[parameters: (...)]`, а там может быть токен. В реферальном коде ловим `SQLAlchemyError` и логируем **только `type(exc).__name__`** и внутренние id; тест это проверяет принудительным сбоем.

### 2. Бонус приглашённого (идемпотентность через план)

В `approve_order` порядок такой (оба пути - `topup` и `new`):

1. План уже сохранён (`plan_computed`) -> берём из `Order` как раньше, **бонус не пересчитывается**.
2. Иначе считаем базовый план (перенос/конверсия триала/новая покупка), затем `claim_bonus(order_id, bonus_bytes)`:
   - Фича включена, у заказа `cash_rub > 0`, привязка в `bound` и без заявки -> атомарный `UPDATE referrals SET bonus_order_id = :order`, и `order_payments.bonus_bytes = bonus` (одна транзакция). Для безлимитного клиента (`new_data_limit is None`) `bonus_bytes = 0`, но заявка всё равно ставится (нужна для награды).
   - Заявка уже принадлежит этому заказу (повтор после сбоя между заявкой и сохранением плана) -> возвращаем сохранённый `bonus_bytes`.
   - Иначе -> 0.
3. `planned_data_limit = базовый + bonus` сохраняется в `Order` **до** вызовов Marzban. Дальше путь прежний (reset -> update / create).

Бонус ГБ - обычные ГБ лимита, поэтому «дальнейший перенос остатка» работает без изменений. Триал-пользователь идёт по пути `build_trial_conversion_plan` (остаток триала не переносится) и получает `+bonus`.

Заявка привязана к конкретному заказу: если у приглашённого два ожидающих заказа, бонус/награду получает тот, чей план посчитан первым; при `reject_order` этого заказа заявка освобождается (`bonus_order_id = NULL`), следующий заказ сможет её взять.

### 3. Награда пригласившего (одна транзакция с `completed`)

`OrderSettlement.complete(order_id, reward_cfg, now)`:

1. `UPDATE orders SET status='completed' WHERE id=:id AND status='pending'`; `rowcount=0` -> уже обработан, выходим без изменений (идемпотентность).
2. Находим привязку приглашённого со `status='bound'`:
   - `bonus_order_id = order_id`: `reward = floor(cash_rub * percent / 100)`. `reward = 0` -> закрыть (`no_reward`). Иначе условный `UPDATE ... rewarded` с проверкой месячного лимита (rowcount 1 -> `INSERT balance_entries(referral_reward, +reward, ref=referral_id)`; rowcount 0 -> закрыть `monthly_cap`). Бонус ГБ приглашённого остаётся в любом случае.
   - заявки нет (`bonus_order_id IS NULL`): это первый подтверждённый заказ без права на бонус (деньгами 0 или фича выключена на момент расчёта плана) -> закрыть (`no_cash`/`not_eligible`).
   - заявка у другого ожидающего заказа -> не трогаем.
3. Коммит. Сбой любого шага откатывает всё, включая `completed`; повтор `approve_order` безопасен (план в `Order`, Marzban-вызовы идемпотентны, `UNIQUE(kind, ref_id)` не даст второй записи).
4. После коммита (вне транзакции, с `try/except`): сообщение приглашённому (как сейчас) и уведомление пригласившему через захват флага `notified_at`; временный сбой -> флаг освобождается, фоновая задача (каждые 5 минут) досылает; `Forbidden`/`chat not found` -> `notify_blocked_at`, больше не повторяем.

### 4. Баланс: резерв при создании заказа (предлагаемый минимальный надёжный вариант)

Как устроены заказы сейчас (проверено в коде): заказ создаётся только после загрузки чека (`receipt_photo_handler`); статусы только `pending -> completed | rejected`; **истечения и отмены ожидающих заказов нет** (отмена на экране оплаты происходит до создания заказа); `reject_order` - единственный выход из `pending` кроме подтверждения; у пользователя может быть несколько `pending` одновременно.

Предлагаю:

1. **Удержание в момент создания заказа.** В одной транзакции: `INSERT orders` -> `INSERT order_payments(price, balance, cash)` -> условный `INSERT balance_entries(order_spend, -hold, ref=order_id)`, который проходит только если `SUM(...) >= hold` в момент вставки. Если условие не прошло (параллельный заказ успел раньше) - откат и повтор с пересчитанным балансом (до 3 раз). Это единственное место, где баланс уменьшается, и оно же гарантия «не в минус» и «не дважды».
2. **Сумма удержания** = `min(баланс, показанный_на_экране_баланс, цена)`: человек перевёл деньги исходя из экрана, поэтому удерживаем не больше показанного, а карточка администратора и ответ пользователю содержат фактические «списано» и «к оплате».
3. **Возврат при отклонении**: `reject_order` в одной транзакции делает `UPDATE orders ... WHERE status='pending'`, `INSERT balance_entries(order_refund, +hold, ref=order_id)` (уникальность -> один раз) и освобождает заявку на бонус.
4. **Подтверждение ничего не списывает дополнительно** - удержание уже и есть списание. Повторы `approve_order` баланс не трогают.
5. **Неподтверждённый заказ**: сумма остаётся удержанной (не потеряна и не может быть потрачена повторно) до решения администратора. Таймера нет сознательно: автовозврат по времени, пока администратор мог уже оплатить заказ вручную, создаёт риск двойной траты (вернули баланс -> заказ подтвердили). Если нужен выход «админ не отвечает» - это отдельное решение (автоотклонение через N дней или команда админа), см. вопрос 2.
6. **Параллельные заказы**: второй заказ видит уже уменьшенный баланс; при нехватке получает меньшее удержание и большую денежную часть (пользователь видит это в ответе «Заявка принята»).
7. **Заказ целиком с баланса**: кнопка «Оплатить балансом» (экран оплаты при `cash_due = 0`) -> заказ с `photo_file_id = 'balance'`, удержание = цена, затем тот же `admin_uc.approve_order(order.id)`. При сбое Marzban заказ остаётся `pending` (баланс удержан), пользователь получает «выдача задерживается», администратор - карточку (текстовую) с «Подтвердить/Отклонить» - ручной шаг только как аварийный. Повторное нажатие кнопки не создаёт второй заказ (`selected_tariff` снимается сразу).
8. **Инвариант**: `баланс = SUM(entries) >= 0` всегда, потому что единственное уменьшение защищено условием вставки; пополнения (`referral_reward`, `order_refund`) положительны и уникальны.

### 5. Конкурентность и транзакции SQLite

- Каждая операция - короткая транзакция на своей сессии; первый оператор - запись (см. data-model.md); обёртка повтора при `database is locked`.
- Тесты на параллельность используют файловую SQLite (как `conftest.py`) и `asyncio.gather`, чтобы реально ловить гонки.
- Уточнение: PTB по умолчанию обрабатывает апдейты последовательно, поэтому в проде настоящая конкуррентность - это фоновая задача против хендлеров и повторные доставки; атомарность БД всё равно обязательна и проверяется тестами.

## Находки в существующем коде (важно для вашего решения)

1. **План сохраняется в `Order` только на пути `topup`.** В `_apply_new_purchase` план (лимит и срок) не сохраняется, `expire` считается заново при каждой попытке, а повторная попытка после частичного сбоя упрётся в `409` от Marzban (`user_<id>_<order>` уже существует) или в `UNIQUE` на `vpn_profiles.marzban_username`. Для первой покупки приглашённого (самый частый случай бонуса) это именно тот путь, поэтому предлагаю: сохранять план перед `create_user` (используются уже существующие колонки `Order`), при `409` продолжать как `update_user` с сохранённым планом, при существующем профиле не создавать второй. Нормальный путь не меняется; нужна ваша отметка в вопросе 3.
2. **`reject_order` не под lock и не условный**: при гонке «подтвердить + отклонить» `approve` может перезаписать `rejected` на `completed` безусловным `update`. Для денег это недопустимо (возврат + списание). Исправляется в рамках фичи (lock + условный `UPDATE`).
3. **Кэш общей сессии**: `get_by_id` на общей сессии `main.py` отдаёт устаревший объект, если строку поменяла другая сессия. Поэтому статус заказа перед `approve/reject` читается через `get_fresh()` (`populate_existing`).
4. **Статуса `confirmed` нет**: «подтверждённый» = `completed`.
5. `receipt_photo_handler` берёт `selected_tariff` по умолчанию `0` (заказ на 0 ГБ без цены) - в новом коде защищаю ранним выходом.

## Риски

| Риск | Смягчение |
|---|---|
| Двойное начисление награды/бонуса при повторах и сбоях | `Order`-план + `UNIQUE(kind, ref_id)` + условные `UPDATE ... WHERE status` + тесты с внедрением сбоев |
| Потеря/двойная трата баланса | Удержание при создании, возврат при отклонении, условная вставка, тесты на параллельность |
| Токен в логах (в т.ч. через текст исключений SQLAlchemy) | Логируем только id и тип исключения; тест с перехватом loguru |
| Устаревший объект в общей сессии | `get_fresh()` для заказа перед решением |
| Блокировки SQLite при параллельных записях | Запись первым оператором + повтор; тесты на файловой БД |
| Изменение `approve_order` ломает перенос остатка/триал | Внедряемые зависимости опциональны, нормальный путь не меняется, все 173 теста остаются зелёными |
| Самоприглашение через второй аккаунт | Награда (30%) не превышает реально оплаченных приглашённым денег, поэтому фича не убыточна; отдельной антифрод-логики нет (риск принят) |

## Принятые решения владельца и итог реализации (2026-10-08)

Вопросы 1-11 приняты с уточнениями (см. `tasks.md`). Что изменилось относительно первоначального плана:

- **Отмена заказа пользователем** (кнопка «Отменить заказ» под «Заявка принята» и под сообщением об оплате балансом): `AdminUseCases.cancel_order` под тем же lock, что подтверждение и отклонение; статус `cancelled`; отказ, если выдача уже начата (`plan_computed`). Подтверждение, отклонение и отмена - взаимоисключающие условные переходы `UPDATE ... WHERE status = 'pending'`.
- **409 на создании пользователя**: профиль переиспользуется только если имя соответствует `user_<telegram_id>_<order_id>` этого пользователя и в БД нет профиля с таким именем у другого пользователя.
- **Число ГБ в текстах** берётся из `REFERRAL_INVITEE_BONUS_GB` (приглашение принято, экран «Пригласить друга»); в сообщении о выдаче - из сохранённого `order_payments.bonus_bytes`.
- **Закрытие привязок ленивое**: при первом подтверждённом заказе приглашённого, если заявка на бонус не была поставлена (оплата балансом целиком или фича выключена).
- **`/balance <id>`** - только просмотр; корректировки нет.
- **Имя бота**: `BOT_USERNAME` главнее `get_me`, расхождение - warning (один раз).
- **Охрана «нет цены»**: при подключённых платежах `approve_order` отказывает, если тариф неизвестен/цена не положительна, нет удержания в журнале, либо денежная часть 0 без полной оплаты балансом (метка `photo_file_id = 'balance'`).
- Кнопка `pay_balance` зарегистрирована как entry point и fallback `ConversationHandler` (работает и после перезапуска бота).
